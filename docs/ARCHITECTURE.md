# 火情 / 烟雾 视频检测 —— 架构说明

> 目标：检测**火焰**与**烟雾（白烟、灰烟、黑烟）**，并把**蒸汽 / 水雾**排除掉。
> 硬约束：**视频输入，不是单帧判别**。

## 一、为什么必须做视频，而不是单帧

白烟和蒸汽在单帧图像里几乎是同一种东西：同为白色、同为半透明、同为上升羽流。
单帧模型只能靠背景和颜色瞎猜 —— 这就是市面上烟雾检测误报率高的根因。

但一旦有时间维度，两者差别很清楚：

| 特征 | 烟 | 蒸汽 / 水雾 | 代码里的量 |
|---|---|---|---|
| 面积增长 | 慢而持续 | 几秒内快速膨胀再变淡 | `area_growth`（对数域斜率） |
| 存续时长 | 数十秒~分钟 | 几秒~十几秒 | `duration` |
| 亮度走向 | 白→灰→黑（碳颗粒） | 始终偏白、只会变淡 | `gray_trend` |
| 边界清晰度 | 相对稳定（有纹理） | 越来越糊 | `edge_trend` |
| 上升速度 | 随浮力，较稳 | 更快、更"抖" | `rise_speed` |
| 与火源关系 | 常伴随明火 | 与火无关（壶口/管道口） | `has_fire_nearby` |

**结论：检测器负责"看见"，时序模块负责"确认是什么"。**

## 一·五、双模采集：固定机位 + 云台（两种都要支持）

两种相机的**背景行为完全不同**，不能用一套采集逻辑硬套：

| | 固定机位 | 云台（PTZ） |
|---|---|---|
| 背景 | 长期不变 → 可建模 | 一直在动 → 建模直接失效 |
| 手段 | 中值背景 + MOG2 取并集 | 先估全局单应，warp 回参考坐标，再差分 |
| 优势 | 能捞到**很淡、很早期的烟** | 覆盖范围大，可巡航发现远处火点 |
| 坑 | 开关灯/日照突变 → 大面积假前景 | 转动中满屏"变化"；同一团烟被拉成多个轨迹 |
| 处理 | 亮度突变检测 → 重置背景 | `moving=True` 时**冻结轨迹与事件**；停稳后重建参考背景 |

采集层契约（`src/sources/base.py`）：

```python
FramePacket(cam_id, idx, ts, image,
            moving,        # 云台是否在转 → 下游必须冻结判定
            homography,    # 当前帧 → 参考帧
            fg_mask)       # 变化区域（固定机位/补偿后才有）
```

实测（`scripts/test_sources.py`，合成数据，11/11 通过）：

| 场景 | 结果 |
|---|---|
| 固定机位：第 30 帧开始冒烟 | 前景重心落在烟心 **2px** 内，烟区覆盖率 **99%** |
| 云台：整幅平移 174px | 估计位移 **174.4px**（误差 0.4px） |
| 云台：补偿后残差 | 37.4 → 11.2，**降 70%** |
| 云台：转动期间 | 29/30 帧标记 moving，**0 帧输出前景**（避免满屏误报） |

> 踩坑记录：合成烟雾时若直接 `circle + GaussianBlur`，会把**整幅图**糊掉（不是只糊圆圈），
> 导致每帧都和背景差很多、掩码满屏 —— 这是测试夹具的 bug，不是检测逻辑的 bug。

## 二、五级流水线

```
 多路视频流(RTSP/文件)  ── 固定机位 / 云台，各一路 worker
     │
 ① capture   抽帧 + 缩放 + 光照归一(CLAHE) + 时间戳 + **背景建模/运动补偿**
     │  FramePacket{idx, ts, img}
 ② detect    YOLO26 逐帧推理 → 候选框 fire/smoke/steam
     │  Detection{cls, conf, xyxy}
 ③ track     Kalman/BoT-SORT 关联 → 轨迹 tracklet
     │  Track{id, samples[...]}
 ④ temporal  轨迹级特征 → 判定 smoke / steam / uncertain   ← 本项目的核心
     │  Verdict{label, score, reasons}
 ⑤ event     连续 N 帧确认 + 冷却期 + 分级告警 → 推给界面/短信
     │  Event{type, level, t_start, snapshot}
```

阶段契约（只传结构体，不传裸数组）：
- `FramePacket`：一帧图像 + 序号 + 时间戳
- `Detection`：类别 + 置信度 + 框
- `Track`：id + 时间序列样本（`TrackletSample`）
- `Verdict`：判定 + 分数 + **人话理由**（现场调参靠它）

## 二·补　LLM 裁判与前端的接线（2026-10-31）

### 分工：LLM 是"参谋"，不是"开关"

YOLO 是触发器，LLM 是判读者，**结论直接推给管理员，不回灌检测链路**。

```
视频帧 ─▶ YOLO ─▶ 轨迹 ─▶ 规则层
                              │
              ┌───────────────┼───────────────┐
              ▼               ▼               ▼
        ① 0.2s 推 notice   ② 异步送 LLM    ③ 规则层自己的结论
        （人立刻看到）     （1~2s 出裁决）   （也推，不压制）
                              │
                              ▼
                       推 alarm / cleared
```

三条硬约束：

1. **异步，绝不阻塞**。`requests.post` 一次 1~1.5s，而 15fps 每帧只有 65ms 预算。
   同步调一次 = 硬卡掉 20 帧视频，卡住的这一秒里真起火就全丢了。
   所以全部走 `ThreadPoolExecutor`：`submit()` 微秒级返回，`poll()` 每帧收割。
2. **只审可疑，不审每帧**。按 15fps 每帧送审算约 1600 万 token/小时/路，纯烧钱。
   火灾是**事件**不是**流**，一条轨迹只判一次 → 成本降到万分之一，延迟还更低。
3. **降级绝不静默**。没 Key / 超额 / 超时 / 返回脏数据 → 回退规则层结论，
   并且**保守放行**（宁可报出来让人看一眼）。

### 送两张图，不是一张

| 图 | 提供什么 | 长边 |
|---|---|---|
| 整幅画面 | 环境线索：灶台？车间？天花板？ | 768 |
| 可疑区域放大 | 细节：火舌？焦黑？颗粒感？ | 512 |

单帧送审等于退回"单帧识别"——白烟和蒸汽在单帧上同色同形，模型只能瞎猜。

### 关键设计：降级也要推，不能静默

「怕蒸汽误报」是本项目最大的陷阱：**只要有一次把真烟判成蒸汽，管理员屏幕上就什么都没有。**
所以判成蒸汽时不但不丢弃，反而要留痕：

| 情形 | 推送级别 | 管理员看到 |
|---|---|---|
| 规则层倾向蒸汽 | `notice` | 「规则层倾向判为蒸汽/水雾，已降级（**不是排除**）」+ 截图 |
| LLM 判为蒸汽/灯光 | `cleared` + `dismissed` | 「**已降级·待复核**」（琥珀色，不是绿色的"已排除"）+ 截图 |
| LLM 拿不准 | `notice` | 推给人自己看 |
| LLM 判为烟/火 | `warning` / `alarm` | 正式告警 |
| 降级后目标还在 | `notice` | 「判为非火灾风险后仍持续 Ns 未消散，请人工确认是否误判」+ 截图 |

规则层的手工特征（面积增长/亮度/清晰度）分不开真烟和蒸汽，判错必然发生。
**所以任何降级都必须在前端留下可追溯的痕迹**，这是"不漏报"的最后一道保险。

两处细节值得单独说：

**① `cleared` 不等于"安全"。** 前端把 LLM 降级的那条渲染成琥珀色的「已降级·待复核」，
而不是绿色的「已排除」，也把它算进"待处理"筛选项。理由很直接：绿底"已排除"会让人
安心地划过去，这恰恰是漏报最危险的样子 —— 没有任何人确认过，只是模型说了句"不像火"。

**② 降级不是永久豁免。** 见下节。

### 裁判说了不算的兜底：`dismiss_recheck_sec`

裁判判"蒸汽"之后规则层会闭嘴（`llm_mute_sec=180`），这本身埋了一个盲区：
真烟被误判一次，接下来三分钟管理员屏幕上一片安静。

所以加一条按**时间**的兜底：判降级之后，这个目标又活了 `dismiss_recheck_sec`（默认 30s）
→ 推一条 `notice`：「判为非火灾风险后仍持续 30s 未消散（共 55s），请人工确认是否误判」。

三个设计取舍：

| 取舍 | 为什么这么定 |
|---|---|
| 按"判完之后撑了多久"计时，不是按目标总寿命 | 用总寿命会把"刚判完立刻复核"算成命中，两张卡同一秒落地，等于没复核 |
| **不重新调 LLM** | 同一个问题问第二遍答案大概率相同，白花配额还多等 1.5s。该做的是把证据摆到人面前 |
| 每条轨迹只叫一次（`_recheck_done`） | 不设上限就变成每分钟弹一次，人很快就学会无视它 |

真蒸汽几秒最多十几秒就散，撑过 30 秒本身就是证据。这条是"不漏报"的最后一道保险。

### 测试结果（合成序列，真 YOLO + 假 LLM）

| LLM 裁决 | 结果 |
|---|---|
| 关闭 | 火 1 条 alarm，0.2s |
| 判 fire | 1 条 alarm，0.2s，score 改用 LLM 的置信度 |
| 判 steam | **0 条正式告警**，但推 1 条 `cleared` 留痕 + 30s 后 1 条 `notice` 复核 |
| 拿不准 | 1 条 `notice`（推给人），0 条 alarm，不触发兜底复核（本来就在等人看） |

### 踩过的坑（都很贵）

1. **裁判判过之后规则层还在抢着定级**。LLM 判"蒸汽"压掉 → 下一帧裁判去重生效（不重复送审）
   → 规则路径接手把同一个目标重新报成 ALARM。等于裁判白判，还多花一次钱。
   → 加 `_arbiter_done`：判过的目标规则层闭嘴。
2. **告警去重按"轨迹"是错的**。模型会把一团火切成好几条轨迹（实测 tid 2/6/7/8），
   每条独立走完流程，30 秒冷却一过重新放开 → 同一场火在 t=1.4s / 31.4s / 61.5s
   各报一次，`cooldown_blocked` 累计 **1577** 次。
   → 改成**命中同区域记录就续期**：只要这个位置还在烧就只报一次，烧完 30 秒后才允许重报。
3. **SSE 长连接会让无头浏览器永远等不到"加载完成"**，截图/自动化测试全部超时。
   → 看板支持 `?nosse=1` 只拉一次历史。

### 推送通道（`src/notify.py`，纯标准库）

- `GET /` 看板 · `GET /events` SSE 流 · `GET /snapshots/<file>` 截图 · `GET /api/recent` 历史
- 先落盘（截图 + jsonl）再广播：宁可晚 3 毫秒，也不能出现"前端有告警、磁盘没证据"
- 断线自动重连，重连后补发最近 40 条历史，不会漏事件
- `--host 0.0.0.0` 可让手机/另一台电脑看；`--webhook` 可转发企微/钉钉
- 路径穿越已防（`/snapshots/../../config/...` → 404）

## 三、类别设计：**3 类，不是 2 类**

```yaml
0: fire    火焰
1: smoke   烟（白/灰/黑）
2: steam   蒸汽/水雾（负类，显式建模）
```

只做 2 类（fire/smoke）时，模型会把蒸汽学成烟雾，误报率压不下去。
显式给出 `steam` 类，等于把"区分"变成一个可训练的目标；推理时对 `steam` 抑制即可，
还能统计"因蒸汽被拦下多少次"，方便评估改造效果。

## 四、训练与评估规范（这两条不做，指标全是假的）

1. **按视频划分，不按帧划分**
   同一段视频的相邻帧高度相似，随机分帧会让验证集泄漏训练集，mAP 虚高 10~20 个点。
   切分单位是**视频**：`data/splits/{train,val}.txt` 里放视频名。

2. **指标看视频级，不只看 mAP**
   | 指标 | 含义 |
   |---|---|
   | 漏报率 | 真实火情里没报出来的比例（最要命） |
   | 误报率 | 每小时的虚假告警次数（决定能不能用） |
   | 确认延迟 | 从起火到报出用了多少秒（安防要求通常 < 10s） |
   | mAP50 | 只作参考，不作为验收标准 |

### M4 实测（2026-10-31，v5 模型 @896、切片 2×2 开）

合成场景跑通全链路，素材取自 test 集的真火/真烟：

| 场景 | 检出 | 确认延迟 | 说明 |
|---|---|---|---|
| 单簇火 | fire 1 次 | **0.2s** | 快路径，连续 3 帧即报 |
| 火 + 烟 | fire + smoke | 火 0.2s / 烟 **1.8s** | 烟靠「旁边有火」先验过线（score 0.83） |
| 只有烟无火 | 12.8s 内不报；28s 时 **26.3s** 报 | **25.1s** | 阴燃只能靠存续时长，**超过 10s 验收线** |
| 蒸汽（负样本） | **0 告警** | — | 判 steam 丢弃 5 帧 |

吞吐（960×540，切片全开）：**15.5~22.6 fps**。

> 两条被实测纠正的设计：
> 1. 亮度/清晰度走向必须等 ≥5s（`trend_min_duration`）。轨迹建立初期框在长大，
>    框内均值被几何变化主导，1.6s 就能算出 -9.5/s 的假「变黑」。
> 2. 静态误报抑制要看**出生期**前景占比，不能看滑动均值。中值背景会把静止的烟
>    吸进背景，用均值判定会在 20s 后开始误杀真实阴燃（实测压掉 109 帧）。
>
> 未解决：无明火的阴燃要 25s 才报，而验收线是 10s。唯一可用的杠杆是 VLM 复核层
> （`src/verifier.py`，已在流水线上留了挂点，默认关闭）。是否启用、额度多少，需要现场定。

### 极快模式（`fast_smoke`，默认关）

「极快反应」和「区分蒸汽」在物理上互斥：白烟与蒸汽**单帧同色同形**，要分开必须
观察一段时间。所以快慢不由代码决定，由**现场有没有蒸汽源**决定。

| 部署场景 | 建议 | 阴燃反应 | 蒸汽 |
|---|---|---|---|
| 机房/配电间/仓库/垃圾房/电池仓/档案室（无蒸汽源） | 开 `fast_smoke` | **0.2s** | 会误报，但场景里本来就没有 |
| 厨房/锅炉房/洗浴间/有加湿器或冷却塔（有蒸汽源） | 保持关闭 | 25s | 正确抑制 |

开启后是**三级**，不是一上来就喊狼来了：

| 级别 | 时间 | 含义 | 是否占告警去重额度 |
|---|---|---|---|
| `notice` | **0.2s** | 极快模式命中，推给值班员看画面，需人工确认 | 否（否则升不了级） |
| `warning` / `alarm` | 1.8s+ | 时序层也判是烟 → 升级为正式告警 | 是 |
| `cleared` | 1.5s | 时序层判成蒸汽 → 自动撤销刚才那条 notice | 否 |

实测（合成序列）：阴燃 `notice` 延迟 **0.2s**；蒸汽 `notice` 0.2s → `cleared` 1.5s，
正式告警 **0 条**。所以"快"和"不误报"可以各自拿到该拿的级别，不必二选一。

> 踩坑：notice 一开始不参与区域去重，结果一团被模型切成 3 段的烟吐出 4 条 notice；
> 而 `cleared` 时又把轨迹从"已通知"集合里移除，导致 notice→cleared→notice 反复抖了 5 轮。
> 现在 notice 有独立的区域去重记录，且一条轨迹的 notice 只发一次。

## 六·补　灯光误报治理：闪烁闸（2026-10-31）

车位灯、路灯、招牌、玻璃反光在**单帧**上和火长得一样：高亮、暖色、局部过曝，
YOLO 必给高 conf（实测合成的一块橙色亮斑能拿 0.87，比场景里的真火还高）。
原来的火路径只看"连续 3 帧命中"，而灯是恒亮的 —— 3 帧稳过，等于零拦截。

火和灯唯一稳定的差别是**抖不抖**：火焰是湍流燃烧，亮度天然带 3~10Hz 抖动；
LED/卤素灯是稳流驱动，亮度恒定。所以闸只看帧间亮度变化，不看形状、不看颜色。

| 指标 | 为什么不用另一种写法 |
|---|---|
| 框内**逐像素**变化占比（灰度差>8） | 框内平均亮度差会被火焰内部的增减互相抵消，同一段视频里动态范围 18 倍；逐像素统计只有 1.4 倍 |
| 减掉**整幅**同步变化占比 | 相机晃动、云影、自动曝光会让整幅一起变，不扣掉就全算成"火在抖" |
| 钉死一块**固定绝对坐标** ROI | 跟着检测框每帧变不行：YOLO 框每帧宽高都不同，逐像素差分永远被跳过（实测 flicker 恒为 0），而且测到的是"框在动"不是"火在抖" |

判定分三档，**刻意偏放行**：

| flicker | 判定 | 动作 |
|---|---|---|
| ≥ 0.25 | `fire` | 正常报警，理由里带上抖动数值 |
| 0.05 ~ 0.25 | `uncertain` | 放行，正常报警（灰区不拦） |
| < 0.05 | `static` | **降级成 notice + 送 LLM 复核，绝不排除** |
| 样本 < 5 帧 / ROI < 300px | `uncertain` | 放行（统计不可靠就别下结论） |

`fire_confirm` 从 3 提到 5：判"抖不抖"至少要 4 个帧间差分，3 帧时闸等于不存在。
代价 0.12s → 0.20s，对火灾尺度无关紧要。

标定与实测：

| 对象 | flicker | 结果 |
|---|---|---|
| 真火连续帧（960×540，113 帧，664 条轨迹） | min 0.200 / P10 0.212 / 中位 0.335 / max 0.599 | 误拦 **0/664** |
| 车位灯（合成恒定亮斑，160 帧） | 0.000 | 拦截 126 次，正式告警 **0 条**，留痕 1 条 |
| 合成慢闪 2% / 5% / PWM 20% | 0.000 | 全判 static |

> 为什么不上"主动学习"打头：灯是**开放集合**（车位灯/路灯/广告牌/红灯笼/电焊/夕阳/
> 圣诞灯串），标完 500 张，下周加个霓虹招牌照样误报，而重训一次 41853 张要 3~5 天。
> 闪烁是物理先验、零标注、当天上线。主动学习仍然要做，但它是第二层（收残留），
> 不是第一层。

## 六·补二　分级检测（`detect_mode`，默认 `auto`）

真实枪机 99% 的帧是空的，而 `sliced=True` 是**每帧固定跑 5 次前向**（整图 + 2×2）。
实测 960×540 @896：单次前向 11.7ms（GPU），5 次 52ms，整条流水线只有 16 fps ——
全是给空白帧付的钱。

改成先粗筛一帧，**粗筛没东西就不切片**：

| 策略 | 真火画面 fps | 空白画面 fps |
|---|---|---|
| `slice`（每帧都切） | 15.1 | 16.3 |
| **`auto`（分级）** | **19.2** | **45.9** |
| `full`（不切片） | 38.8 | 48.1 |

召回（test 集 100 张，IoU≥0.5）：`slice` fire 68.5% / smoke 69.2%，
`auto` fire 67.8% / smoke 68.5%，`full` fire 55.0% / smoke 58.2%。

> 那 0.7pt 不是触发逻辑丢的，是**批量前向**丢的：ultralytics 只在单图时用
> `auto=True` 的最省 padding，批量时统一补成方形，输入几何略有不同。
> 同样一批"切片但逐张跑"是 68.5%，"切片的批量版"是 67.8% —— 两者算的是同一批图。

> 走过两条弯路，都记下来免得再走：
> 1. **只补可疑区域**（围着候选框裁 1~3 块小片）比全切更省，但 fire 召回掉到 61.7%。
>    候选框漏掉的区域就是永远补不到的区域，等于把"没看见"固化成了"没看见"。
>    切片的价值是**整幅无死角放大 3.3 倍**，不是把某一块放得更大。
> 2. **单次高分辨率整图**替代切片：1280 只到 58.4%，1536/1920 反而更差。
>    要等效 3.3 倍得 3200 输入，不现实。

## 七、还没解决 / 需要现场确认

- 摄像头是**固定机位**还是云台？（决定要不要背景建模）
- 最小可接受告警延迟？（决定确认帧数 N）
- 是否有**红外/热成像**通道？（有的话火情判定会简单一个量级）
